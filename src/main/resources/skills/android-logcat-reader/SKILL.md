Analyze Android logcat session files generated by the custom plugin under `AppLogs/`.
Each file represents a single session and contains:

* Device name
* Timestamp in filename
* Raw logcat output

## When to use

Use this skill when:

* User asks about logs, crashes, errors, or debugging
* User references files under `AppLogs/`
* User pastes logcat output or mentions "session logs"

## File location

All logs are located relative to project root:

```
AppLogs/*.txt
```

Example:

```
AppLogs/google-pixel_9_pro_xl-adb-XXXX_2026-04-20_22-10-56.txt
```

## File naming convention

Filename format:

```
<device-name>-adb-<connection-id>_<timestamp>.txt
```

From this you can extract:

* device = google-pixel_9_pro_xl
* timestamp = 2026-04-20_22-10-56

## How to analyze logs

### Step 1 — Identify session context

* Extract device name
* Extract timestamp
* Assume logs are chronological

### Step 2 — Scan for critical issues

Look for:

* `E` → errors
* `W` → warnings
* `FATAL EXCEPTION`
* `ANR`
* crashes or stack traces

### Step 3 — Focus on app logs

Prioritize logs from the app package:

```
com.david.h.myspots
```

### Step 4 — Ignore noise

Ignore:

* system logs (unless related to crash)
* verbose logs (unless related to crash)

### Step 5 — Extract meaningful events

Summarize:

* app start
* initialization
* user actions (if visible)
* failures

### Step 6 — Provide structured output

Always answer with:

1. 🧾 Session summary
2. ⚠️ Issues found
3. 🔍 Root cause (if possible)
4. 💡 Suggested fix

## Example interpretation

Input log snippet:

```
E h.myspots.debug: No package ID 6a found for resource ID
```

Interpretation:

* Resource mismatch or corrupted build
* Likely R file / resource issue

## Special rules

* If no errors → say system is healthy
* If multiple errors → rank by severity
* Always explain in plain English
* Prefer actionable fixes over theory
